# Data handling

`ALLOW_CLOUD_PROCESSING` defaults to false. Real classification, extraction and drafting calls are blocked until you explicitly enable it. The provider receives the sender/subject and up to `MAX_BODY_CHARS` of the body; drafting additionally includes a bounded recent thread context and the configured style template. The provider and model are selected by `LLM_MODEL`. Review that provider's account data controls before connecting a real mailbox.

`REDACT_PII=true` masks common email addresses and phone-number patterns before LLM requests. It is best-effort masking, not anonymization: names, account numbers, addresses, signatures, invoice contents and other sensitive details may remain. Numeric matching can also mask some invoice/order identifiers; disable it only after making your own data-sharing decision. Prompts treat email fields as untrusted data; this reduces prompt-injection risk but is not a complete defense. Keep human review enabled for uncertain classifications and all outbound sends.

Refresh tokens are Fernet-encrypted at rest. The encryption key is separate from the database and must be backed up securely; losing it requires reconnecting accounts. Email bodies, extracted entities, drafts, sender/subject metadata and audit rows are otherwise stored in Postgres. Use encrypted disks/backups and restricted database access. API response DTOs do not expose refresh tokens. Provider failures are recorded by error type rather than raw error bodies.

The graph checkpoints store IDs/status/decisions rather than email bodies. LangSmith tracing is off by default. Enabling it can send email inputs and model outputs to another third party; do not enable it merely to troubleshoot sensitive mail. Gmail OAuth callback query parameters contain authorization codes/state, so supplied startup commands disable Uvicorn access logs. Configure proxy logs to omit callback query strings too.

`make retention` (or the Compose maintenance service) clears bodies, extracted entities and threading headers for completed messages older than `RETENTION_DAYS`, excluding messages with unfinished drafts. It clears old sent/rejected draft bodies as well. It does not delete email from Gmail, remove pending-review content, erase sender/subject metadata, classifications, audit history, checkpoints or backups. This is content minimization, not a comprehensive personal-data erasure mechanism. Run the command daily through your scheduler; it is not enabled automatically. Database backups need a separate retention policy.

Knowledge documents and owner-written preferences are also stored as plaintext in Postgres. Relevant excerpts and preferences are included in draft planning/composition/verification requests after the same best-effort redaction. Draft records retain source snapshots and verification findings; deleting a knowledge document invalidates associated drafts but does not erase existing snapshots. Retention clears source snapshots and verification reports along with old sent/rejected draft bodies. Owner-managed knowledge/preferences persist until explicitly edited or removed. Agent timelines retain structured tool names, counts, error types, timings and optional token usage rather than raw messages or private reasoning.
